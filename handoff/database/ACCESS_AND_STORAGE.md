# Access and storage contract

## Permission evaluation
For every user command, derive actor from verified `auth.uid()`. Require active profile, unexpired/unrevoked assignment, correct institution/organizer/event, correct duty where applicable and verified MFA `aal2` for staff. Reject conflicting participation for judging/payment review. User metadata, local storage, route names and requested role are never authority. Super admin must also be active and MFA-verified.

Prefer private helpers `app.require_actor()`, `app.require_staff(capability,event_id)` and narrowly scoped read filters. Every SECURITY DEFINER function sets `search_path=''`, qualifies names, revokes PUBLIC execution and grants only its intended role. Avoid helpers with user-controlled actor parameters. Helper functions belong in unexposed `app`; public RPC wrappers are the deliberate API. Don't expose a generic SQL executor, generic table writer or unrestricted status setter.

## Read surfaces
| Caller | Permitted projection | Required restriction |
|---|---|---|
| Anonymous | Published event cards, approved rules/prices, published schedule and result display names | No profiles, transactions, draft config or room secrets |
| Student | Own profile, registrations, accepted team roster summary, own payment status, own pass, own inbox | No bank statements, token hashes, other members' contact/payment details |
| Captain | Own registration and minimal member invitation/consent state | No member passwords, private IDs or ability to consent as member |
| Teacher | Own assignments and explicitly assigned coordination data | Affiliation alone grants no event roster access |
| Volunteer | Minimal participant identity/eligibility after valid lookup within duty | No full exports, payment evidence, bank data or unassigned rosters |
| Judge | Assigned entry presentation and own scorecard | No other judges' drafts, participant payment evidence or competing entries outside assignment |
| Event admin | Organizer/event operations summary and allowed workflow queues | Finance/export data only with separate explicit grant |
| Finance reviewer | Scoped orders, authorized evidence, credit matches and refund work | No own-entry verification; no beneficiary changes |
| Super admin | Authorized institution operations and audit | Sensitive changes still require independent approval and reasons |

Return allowlisted DTOs, not `SELECT *`. Do not hide confidential columns only in the UI. Use privacy-preserving 404/403 responses for unauthorized IDs and rate-limit token/reference lookups. Fresh database permission checks prevent revoked roles from continuing through old JWTs.

## Storage buckets to create during implementation
| Bucket | Access | Allowed contents | Policy |
|---|---|---|---|
| payment-evidence | Private | JPEG, PNG, PDF; maximum 5 MB | Own authorized order upload; validated finance-only review |
| official-payment-qr | Private | Approved PNG/JPEG QR | Super-admin controlled upload; narrowly served approved active QR |
| entry-attachments | Private | Approved project images/PDF, maximum 5 MB | Entry owner writes; assigned judge/admin reads |
| poll-evidence | Private | Poll proof images/PDF, maximum 5 MB | Scoped organizer records; authorized reviewer reads |
| incident-evidence | Private | Approved supporting files, maximum 5 MB | Incident-authorized staff only |
| private-exports | Private | CSV/PDF generated by server | Requester with still-valid permission; short expiry |

Public brand images are copied from the approved asset library into the web app, not mixed with private uploads. The official QR may be shown to authenticated checkout users only as an approved current payment profile; serving the image must not expose a bucket listing or historic destinations.

## Upload sequence
Authenticated route validates owner/order/state, rate limit and proposed type/size, allocates a random object path and a short-lived signed upload. Client uploads directly to the private bucket. Finalization verifies actual stored bytes/type/size, computes hash and scans or safely decodes supported content. Record quarantined until validation succeeds. Signed upload URLs are bearer capabilities: do not log them, reuse predictable paths or allow overwriting another order's evidence. Invalid files are rejected and removed under a documented cleanup job.

The SQL `files` row is domain metadata; Storage object creation/deletion and file scanning are external side effects. Handle interrupted uploads and orphan objects through a reconciliation job. Do not pretend a database transaction makes Storage and bank/email operations atomic. Use upload intents and finalize/retry behavior with idempotency.

Download route rechecks current scope before issuing a very short-lived signed URL. Minimize its expiry because a revoked staff session cannot retract an already-issued URL. Apply private/no-store headers and content disposition to evidence. Public SVG/HTML uploads are not allowed. CSV exports must neutralize spreadsheet-formula injection and avoid excessive personal information.

## Baseline policy deployment
001_schema_design.sql intentionally defines no open table policy. Do not expose `app` in Supabase API settings. Implement and test explicit public RPC grants in a second migration, Storage buckets/policies in another, and validated source seed data separately. If a future integration requires direct RLS reads, document the change, use security-invoker views/column grants and run leak tests before enabling it. Do not grant service_role broad app-schema access merely to avoid implementing authorized commands.
